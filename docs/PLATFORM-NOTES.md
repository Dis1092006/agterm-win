# PLATFORM-NOTES

Documented adaptations and divergences of the Windows port from upstream agterm (for the parity policy, see README.md). Each entry says what differs, why, and how it behaves on the wire.

## Phase 1 (AgTerm.Core)

- **`Session.DisplayName` basename and path separators.** Upstream uses `NSString.lastPathComponent` (only `/`). The Windows port accepts both separators (`/` and `\`): the spec's pinned cases still hold (`/` → `/`, `/a/b/` → `b`, `""` → `~`), and in addition `C:\git\proj` → `proj`. This does not affect the wire protocol; it only computes the sidebar label.

- **`PersistenceStore`.** The file format is the same JSON snapshot (field names byte for byte), but upstream writes prettyPrinted+sortedKeys, and the port writes compact JSON without sorted keys. The contract is the field names and types and the decoding rules, not the byte layout of a local file.

- **State directory: `~\.agterm-win`** (instead of `%LOCALAPPDATA%\agterm` from spec §3). Order: `%AGTERM_STATE_DIR%` → `%USERPROFILE%\.agterm-win` → `<temp>\.agterm-win` (the last one matches upstream's fallback `no $HOME → /tmp`). The directory name differs from upstream's `agterm` because the pipe name is derived from the path: with the same name, two different apps on one machine would share state and the control channel. The root is the home directory, as for the CLI tools that drive the app (`agtermctl`). No wire effect: `--socket` and `AGTERM_STATE_DIR` work as before. `PersistenceStore.RealUserDirectory` and `AgtermctlOptions.SocketPath` must derive the same path, otherwise the CLI does not find the app.

- **The config directory sits next to the state** (instead of `%APPDATA%\agterm` from spec §3). `keymap.conf` is looked up where `AppSettings.configDirectory` points, otherwise in the state directory, so by default it is `~\.agterm-win\keymap.conf`. `%APPDATA%` is not used anywhere: all app state and config live in one directory, as for CLI tools.

- **Guard on the default directory under tests.** `PersistenceStore.DefaultDirectory` throws `InvalidOperationException` when a test host reaches it without `AGTERM_STATE_DIR`: a test that fell through to the implicit default would overwrite the developer's real state. `RealUserDirectory` bypasses the guard. It is needed to derive the pipe name (a pure string, no disk access), and state must not be read or written through it.

## Phase 2 (control plane)

- **Structural event coalescing.** `LiveApplicationHost` coalesces `tree.changed` per window after 100 ms of quiet, matching upstream `WindowLibrary`. Store drafts and application-level window changes share the same scheduler. Other event kinds append immediately. Closing or deleting a window flushes its pending invalidation; application shutdown and `FlushTreeEvents()` flush all windows, including removed records. Timers run on the thread pool and serialize publication and flush under a separate gate; callbacks from cancelled timers cannot publish an old invalidation. The existing `Debouncer` does not join an in-flight callback on flush and can run an old timer callback after rescheduling, so this scheduler uses identity-checked timers instead. Standalone `HeadlessHost` and `LiveControlHost` harnesses still forward drafts immediately; production windows use `LiveApplicationHost.AttachWindow` and its coalescing sink.

- **AppStore and threads.** Upstream `AppStore` is isolated on `@MainActor`. In the port the class is also NOT thread-safe, but .NET has no actor, so the host must serialize access itself (the headless host and the pipe server wrap dispatch in one lock). `Debouncer` and the pending-close grace timers fire on the thread pool and call the callback directly (upstream goes through the main queue); the deferred action is responsible for its own marshalling.

- **Auto-follow re-arm without Observation.** Upstream re-arms the idle timer through `withObservationTracking` over `attentionSessions` (deferred, coalesced on the runloop). The port has no Observation and no runloop: `SetAgentIndicator` (the only place that mutates the attention set) re-arms the debouncer directly when auto-follow is on. The semantics are the same: a change of the attention set while the feature is on gives the block the same idle grace as a key press. The `NotificationCenter` notifications (`.agtermAutoFollowed`, `.agtermSidebarVisibilityChanged`) are replaced by the C# events `AppStore.AutoFollowed` / `AppStore.SidebarVisibilityChanged`.

- **Transport: named pipe instead of a unix socket (spec §5).** The channel has no file path. The pipe name is derived deterministically from the SAME socket path (`ControlResolve.SocketPath`, `<state dir>\agterm.sock`): `agterm-<sha256(path)[0..12] hex>`, so isolation by `%AGTERM_STATE_DIR%` is kept. `%AGTERM_CONTROL_SOCKET%` stays an explicit override and holds the LITERAL pipe name (without the `\\.\pipe\` prefix). Connection semantics match upstream: one connection is one request, newline-delimited JSON, a 1 MiB line limit, a per-read timeout of about 5 s plus an overall deadline of about 10 s for read and write, a serial accept loop (one pipe instance). ACL: `PipeOptions.CurrentUserOnly`, the analogue of owner-only `chmod 0600` on the socket file. Idempotent start: a pipe has no stale file to unlink, so a repeated `Start()` is a no-op. Transport error strings are pinned: `"request too large or read failed"`, `"invalid request: <decoder message>"` (the prefix is the contract, the suffix depends on the platform; upstream writes Foundation's `localizedDescription`), and `"debug.appearance is a UI-test-only seam"` for the only command the dispatcher rejects (a UI-test seam outside parity).

- **`RecentClosedStore`.** Local file `recent-closed.json`: field names 1:1, `closedAt` is encoded as a double of seconds since the reference date 2001-01-01 (the Swift `JSONEncoder` default) so that both sides can read it. Upstream writes prettyPrinted+sortedKeys; the port writes compact JSON, atomically (like `PersistenceStore`).

- **Headless host (`HeadlessHost`/`HeadlessControlActions`).** A full implementation of `IControlActions` over ONE `AppStore` (single window; the upstream target resolver is collapsed onto one store, wire error strings are unchanged). Divergences that come from having no windows and no terminal engine:
  - `window.new/close/resize/move/zoom/fullscreen` → `"window management is not available in the headless host"` (after target resolution; the `no such window` and prefix errors are pinned); `window.select` of the only window → ok+id; `window.rename` works; `window.delete` → the exact upstream `"cannot delete last window"`. `window.list`: `geometry`/`fullscreen`/`zoomed` are omitted.
  - Terminal arms go through the `IHeadlessSurface` seam (fake E2E surfaces); the realize polling (~360 ms) is replaced by one check; error strings (`session not realized`, `quick terminal not open`, `no selection` and so on) come from upstream.
  - `session.status --sound` validates against the Windows/user WAV catalog before resolving the target or mutating the status, as in the pinned upstream, but the headless host does not play audio; `notify` always takes the banners-off path (`result.text` = BannersOffNote); `session.search` counts matches in the fake's buffer synchronously; `session.reveal` selects the session (no file manager) and keeps the check that the cwd exists; `config.reload` is an injectable counter (there is no engine); the batch grace of `session.close` is off by default (the finalization timer would live outside the dispatcher lock) and an option turns it on.
  - Bootstrap as in the app: load the snapshot from the state directory (launchRestore armed); an empty state gives the default workspace and a session in home.

- **`agtermctl` (AgTerm.Cli).** Subcommands, flags, validation and output are 1:1 with agtermctlKit; the parser is System.CommandLine instead of swift-argument-parser (the `ParseAsRoot`/`MakeRequest`/`Validate` seam is kept for the ported tests). Socket path resolution: `--socket` → `%AGTERM_STATE_DIR%\agterm.sock` → `%USERPROFILE%\.agterm-win\agterm.sock` → `<temp>\.agterm-win\agterm.sock` (the analogue of upstream `$HOME/Library/Application Support` → `/tmp`); the pipe name is derived from the path (see the transport entry). The help text of `window fullscreen` does not mention macOS (help is not part of the wire contract).

## Phase 3 (terminal engine)

- **Default shell instead of a login shell.** Windows has no `$SHELL` and no login-shell semantics (upstream spawns the user's login shell). The port's policy (`ShellResolver`): an explicit setting is used verbatim; otherwise PowerShell 7 (`pwsh.exe` on PATH); otherwise Windows PowerShell (`powershell.exe` on PATH, present in every supported Windows); otherwise `%COMSPEC%`; otherwise the literal `cmd.exe`. Without pwsh the pane used to open `cmd.exe`, which has no history search (Ctrl+R) and no PSReadLine integration; Windows PowerShell 5.1 has both. Custom commands skip this step (`ShellResolver.ResolveCommandLineShell`: pwsh → `%COMSPEC%`): a line written for pwsh or cmd may contain `&&`, and 5.1 does not accept it. No wire effect.

- **Tokenizing `session.new --command`.** Upstream hands the string to the libghostty config parser. Here the tokenizer is the port's own (`CommandTokenizer`), and the §6 contract holds (quote-aware split, argv[0] is executed directly, shell operators are NOT interpreted): whitespace separates, `'...'` groups literally, `"..."` groups with the escapes `\"` and `\\`, a backslash outside quotes is an ORDINARY character (bare `C:\paths` must survive), an unclosed quote takes the rest literally. Argv → CreateProcessW command line is the exact inverse of the CommandLineToArgvW rules (`WindowsCommandLine`).

- **ConPTY spawn and std handles.** `CreateProcessW` without `STARTF_USESTDHANDLES` duplicates the host's (possibly redirected) std handles into the child, and the child's output bypasses the pseudoconsole (it goes to the host's stdout). The port passes `STARTF_USESTDHANDLES` with null handles (the Windows Terminal ConptyConnection workaround), and conhost replaces them with the pseudoconsole's own handles.

- **Surface realization (replacing Observation and SwiftUI rendering).** Upstream realizes a surface when SwiftUI draws the shown pane. In the port the store has the seam `AppStore.SurfaceRealizer` (the same precedent as the auto-follow re-arm): both "show" paths (SelectSession and AddSession select:true) call it for a main pane without a surface; background creation (--no-select) stays unrealized, and the parity error `session not realized` is kept. Restore() sets the selection without SelectSession, so after the bootstrap restore the host calls `RealizeActiveSession()` (the analogue of the window's first draw). The `AppStore.SelectionChanged` event replaces Observation over selectedSessionID for the window chrome.

- **LiveControlHost (the app).** The headless host's control plane plus real surfaces (`XtermPaneSurface`): realization blocks the dispatcher thread for up to ~15 s (the upstream analogue of realize polling); the UI half (`OpenSurface`) creates the WebView2 pane on the UI thread. Threading rule: the UI thread NEVER takes the host gate, otherwise it deadlocks against the blocking realization. Surface callbacks (OSC title/cwd, exit) hop to the pool and mutate the session under `RunLocked`. When the main pane's shell exits, the host calls `ClosePrimaryPane` (the upstream path); a session with `--command --wait` stays open (`closeOnShellExit` was added later, see "A shell pane stays open when its shell fails"). In phase 3 the quick, scratch, split and overlay surfaces were not implemented yet, and their arms answered with pinned errors. The snapshot is written on exit (Dispose → Save and teardown of all panes).

- **`session.text` and soft wraps.** Reading the buffer joins xterm's soft-wrapped rows into logical lines (otherwise a wrapped long command reads as two "lines"); `--lines N` is the last N lines of CONTENT (trailing empty viewport rows are dropped). Plain text comes from the buffer API (`translateToString`), NOT from the serialize addon: that addon emits VT/SGR sequences, and the `session.text` wire contract is plain text (the serialize addon is bundled and the host uses it to serialize the screen, not for session.text).

## Phase 4 (sidebar and multiple sessions)

- **One WebView2 per window, many xterm.js panes (bridge v2).** Phase 3 kept a WebView2 per session (~100+ MB of runtime and a slow `EnsureCoreWebView2Async` for each). Now the window loads `terminal.html` once; `bridge.js` keeps a registry of panes by `paneId`, and every message in both directions and every `agterm.*` call is addressed by pane (`XtermPage` is the C# owner of the page, `XtermTerminal` is the per-pane handle). Switching sessions shows and hides divs (`agterm.showPane`) instead of changing the WebView2 Visibility. The surface's `PaneToken` (`AGTERM_PANE_ID`) and the bridge's `paneId` are the same identifier. No wire effect. The token stays the bridge pane id for every surface, but it is exported as `AGTERM_PANE_ID` only to main, split and scratch (see "Session environment").

- **Eager deck in the live host.** The upstream app realizes the view of every session as soon as it appears in the deck, so `session.type` reaches a background session without `select`. Port: `AppStore.EagerSurfaceRealization` (the live host turns it on): `AddSession` also realizes `--no-select` creations, and the bootstrap after restore calls `RealizeAllSessions()`. The headless host does NOT turn the flag on: there, tests attach surfaces from outside, and the parity error `"session not realized"` stays as it is.

- **`AppStore.SidebarChanged` (the Observation replacement for the sidebar).** A coarse C# event "something in the sidebar rows changed", following the `SelectionChanged` precedent (phase 3): `Save()` raises it (any persisted mutation), and so do the paths that do not save (selection before the debounce, indicators, unseen). The public `NotifySidebar()` is for out-of-band invalidations from the host (live OSC title/cwd, the unseen bump of the notify arm). The event ring is NOT touched: flag, collapse, focus and mode still do not emit `tree.changed` (wire parity). UI layer: `SidebarController` takes a `SidebarProjection` snapshot UNDER the gate and marshals it to the UI; sidebar gestures call the same store mutators as the socket arms (a third caller, as the upstream toolbar, menu and control channel are).

- **Keyboard Shortcuts view (Windows UI only).** Help > Keyboard Shortcuts and Ctrl+Shift+F1 open a separate read-only overlay with search and action groups. It shows all 41 builtin actions with effective Windows defaults and user overrides, unbound actions, custom commands and leader sequences, physical shortcut conflicts, and parser diagnostics. Conflict rows name the action or command that receives the chord. A parser-rejected custom shortcut remains unbound. Search matches names, identifiers, groups, chords, status and diagnostic text. Reload updates an open list after the terminal accepts the new hotkey manifest and keeps the query. Esc or Close dismisses the list and returns focus to the active terminal pane. The opener chord is fixed and is not in `keymap.conf`; it cannot be rebound or unbound there. F1 is outside the keymap grammar, so the opener does not collide with user bindings. The internal page event does not add a builtin action or a control command. Parser diagnostics stay in an internal snapshot; `keymap.reload` still returns only its existing diagnostic count and emits the same events. There is no new unbind syntax. This view has no upstream equivalent and does not change the parity surface.

- **Keymap modifier mapping on Windows (spec §9: "cmd → Win/Ctrl, as preferred").** Chosen: `cmd`→**Ctrl**, `ctrl`→Ctrl, `opt`→Alt, `shift`→Shift. Two keymap modifiers share one physical key, so a key press is decoded into CANDIDATES by priority: the cmd interpretation, then ctrl, then the folded ctrl+cmd. The first one the matcher knows wins (`WindowsChordDecoder` + `HotkeyRouter`).

  **Windows has its own chord defaults (`WindowsDefaultChords`).** Folding `cmd`→Ctrl put 13 actions on bare Ctrl, and in a Windows terminal bare Ctrl belongs to the shell: Ctrl+D ends input, Ctrl+Z suspends, Ctrl+W deletes a word, Ctrl+P walks history. An app that intercepts them breaks the program in the pane, not only convenience. So every action that would land on bare Ctrl ships on Alt with the same key: `new_session` → Alt+N, `toggle_split` → Alt+D, `session_palette` → Alt+P and so on.

  The criterion is where the chord lands physically, not which modifier the macOS table had: the user does not see the original modifier, and on a keyboard without a Command key it describes nothing. Everything that carries Shift or Alt (`Ctrl+Shift+…`, `Ctrl+Alt+…`) stays where it is: the shell does not read such combinations, and every chord that matches macOS is one less to relearn.

  `BuiltinAction.DefaultChord` is not touched and is still checked against `parity/surface.json`; `WindowsDefaultChords` is a layer over it, in the same place as the `cmd`→Ctrl fold. A `map` line in keymap.conf overrides both. This is a divergence from the original: in `Ported/KeymapTests.cs` the changed expectations are marked line by line, so the file can still be compared with the Swift tests.

  A side effect: `toggle_fullscreen` became reachable. Before, ⌘F (`toggle_search`) and ⌃⌘F (`toggle_fullscreen`) both folded into Ctrl+F, the first one won, and full screen could not be reached from the keyboard at all. Now they are Alt+F and Alt+Enter.

  Two default collisions remain (the shadowed action is reachable through `map`):
  | Physical | Wins | Shadowed |
  |---|---|---|
  | Ctrl+Alt+↑ | `previous_session` (⌘⌥↑) | `previous_attention_session` (⌃⌥↑) |
  | Ctrl+Alt+↓ | `next_session` (⌘⌥↓) | `next_attention_session` (⌃⌥↓) |
  Both carry Alt and do not disturb the shell, so they are left as they are.

  Terminal interception: the page receives the active physical chords (`agterm.setChords`).
  A matching keydown does not reach the shell; xterm's `attachCustomKeyEventHandler` sends
  `{type:'chord',…}` to the host. No default bare Ctrl+letter enters this table, but a user
  `map` can add one. For a non-Latin letter the chord uses its `KeyboardEvent.code` position
  (`KeyF` to `f`); a typed Latin letter wins, including on Dvorak. The full action table
  follows below and in the README.

- **Custom-command shell and chord adaptation.** Upstream executes each custom command as an
  opaque `/bin/sh -c` line. Windows resolves `pwsh.exe` from `PATH` first and runs
  `-NoLogo -NoProfile -NonInteractive -Command <line>`; when PowerShell 7 is unavailable it
  falls back to `%COMSPEC% /d /c "<line>"`, skipping Windows PowerShell even though an interactive
  pane uses it. The cmd fallback uses its command-string quoting
  rule so quotes already written by the command author around Windows paths remain part of the
  shell line. The runtime does not tokenize the line or add quotes around `{AGT_X}` expansions.
  It exports the same ten `AGT_*` values, with `AGT_SOCKET` containing the literal named-pipe
  override used by `agtermctl`, and uses the active session cwd when one exists. A sessionless
  keybind may run only when its command body does not reference session, workspace, or selection
  values; the palette path still requires an active session. The shared WebView2 receives one
  generation-stamped manifest containing active built-ins and parsed custom single/leader chords.
  Replacement is atomic and cancels any armed leader; stale generation events no-op in the host.
  The command gets no `AGTERM_*` value: all seven names are removed from the inherited
  environment (see "Session environment").
  Ported from upstream `babc760`: a custom command puts the bundled `agtermctl.exe` folder first
  on its own PATH, then keeps inherited folders in order, dropping empty and duplicate entries.
  Windows has no launchd default PATH or separate standard CLI install folders; pane shells are unchanged.
  A 1.5-second leader timeout and Escape abandon the prefix, and an unmatched continuation is
  retried at the root before it is returned to the terminal.

- **Sidebar folder import.** Explorer directory drops use the WinUI storage-item format and a
  copy operation. Drops are accepted only in tree mode. A row drop targets that row's workspace;
  empty space falls back to the focused workspace and then the current workspace. Non-directory
  items are ignored, source order is preserved, and one session is created for each of at most 20
  accepted directories. Spring-hover expansion of a collapsed workspace remains a Windows
  adaptation: WinUI drag-and-drop does not expose a stable hover-expand lifecycle, and adding a
  separate timer would conflict with ListView reorder feedback.

- **Close and flagged confirmations.** GUI session closes honor `confirmCloseSession`; single and
  multi-session dialogs snapshot immutable targets, run outside the store and application gates,
  and revalidate the complete target set before applying the close. A stale multi-session target
  aborts the whole operation. Clear Flagged always confirms a non-empty bulk change and removes
  flags only from the sessions shown by that prompt. The named-pipe control API does not show GUI
  dialogs and keeps its existing response semantics.

- **Close undo and recent items.** `closeGraceUndoEnabled` defaults to enabled, matching upstream.
  A per-window InfoBar presents the current three-second pending close and undoes its exact ID.
  Grace expiry runs through the owning host gate, and window shutdown finalizes hidden pending
  records while still awaiting their exact terminal surfaces. Persistent recent items are shared
  by all application windows; Ctrl+Shift+T restores the latest item into the invoking window, and
  concurrent windows cannot consume the same item twice.

- **Live failure presentation.** Terminal spawn and WebView2 initialization failures, settings
  reload failures, and live theme apply failures use one closable in-window error InfoBar. The
  existing failed-terminal row state remains visible. Failure presentation is UI-only: surface,
  config, and theme wire responses and error strings are unchanged.

  When the 15-second terminal realization budget expires, the host logs the surface slot and timeout and reports `Terminal failed to start` through the same InfoBar route. Request cancellation, window shutdown, session teardown, and replaced surface slots do not report a timeout failure. The wire error remains `session not realized`.

## Phase 4.5: live orchestration

- **Bounded terminal output batching.** Each live pane routes ConPTY output through one
  bounded channel before it reaches WebView2. `OutputQueueMaxBytes` is 1,048,576 bytes,
  the item limit is 256 chunks, `OutputBatchMaxBytes` is 65,536 bytes, and
  `OutputFlushInterval` is 8 ms. The ConPTY reader waits when either queue limit is
  reached, so pipe backpressure reaches the child instead of growing the managed UI
  queue. The managed-memory bound also includes one reusable batch buffer and at most one
  carried chunk suffix, so the default peak is about 1,179,648 bytes
  (`OutputQueueMaxBytes + 2 * OutputBatchMaxBytes`). Normal process exit waits for reader
  EOF and the final renderer batch; teardown cancels blocked producers and a renderer
  callback that can no longer complete.
- **Output-pump measurement (2026-08-26, Debug, .NET SDK 10.0.201).** A deterministic
  10 MiB stream completed with the expected SHA-256 at 268.2 MiB/s. It used 160 renderer
  flushes, blocked the producer 55 times, and reached 1,048,576 maximum queued bytes.
  These values record the development-machine stress run; the limits above are the
  implementation contract, not the measured throughput.
- **Ordered live shutdown.** The first WinUI close request is canceled while the live host
  stops pipe acceptance, cancels and awaits active or queued surface realization, stops
  every output pump, saves the snapshot, terminates ConPTY children, and awaits renderer
  removal while WebView2 is still alive. The final close re-enters once after shutdown.
  Surface and renderer waits use a 5-second budget. Shutdown-triggered process exits do not
  remove sessions from the store or snapshot; a five-session live test verifies that all
  children exit, all pane IDs disappear from the page, and all five sessions remain persisted.
- **Windows list/details shell.** The live window uses the Windows App SDK 1.7 `TitleBar`
  above a `SplitView`: the custom multi-select sidebar remains the pane and the shared
  WebView2 remains the content. The pane is inline from 720 effective pixels and overlays
  below that breakpoint. Its persisted width remains clamped to 160..560 pixels; the 4-pixel
  drag target overlays a 1-pixel system divider and saves only on pointer release. The title
  bar shows the accepted session name and owning workspace from one immutable layout
  generation. The shell uses `MicaBackdrop` plus WinUI system theme resources, which provide
  the solid fallback and high-contrast resource variants without a separate color palette.

- **S2 sidebar gestures, keyboard parity, and live-only status projection.** Workspace row tap, Enter, and Space now toggle collapse immediately with no 350 ms delay. Workspace double-click has no rename action. Rename is exposed through F2 and the workspace or session context menu. Session single-click and Enter activate the selected session. Ctrl and Shift modifiers keep standard Extended multi-selection behavior, and Space keeps ListView selection semantics. Keyboard ContextRequested opens the same workspace and session menus as pointer context actions. SidebarSnapshot now carries immutable live-only surface status values (pending, ready, failed) so the UI reports terminal lifecycle without changing Core `SidebarRow` shape, tree JSON, or wire protocol fields. Session rows show pending and failed visual indicators from that status projection. UI Automation names now cover workspace and session selection state, lifecycle status text, agent status text, unseen count text, focused-workspace state, flagged-toggle state, and the new-workspace action. Manual Narrator verification is not claimed yet.

- **S3 capability-aware command routing.** The WinUI window classifies all 41 upstream builtin actions in one router, and every action has an explicit handler. Actions without a default chord remain available through the title bar, sidebar, context menus, or palettes as applicable. These entry points and hotkeys use the same router or the same selection-aware `SidebarController` store operation. xterm.js receives only physical chords whose effective Windows winner has an explicit handler. The cmd-to-Ctrl adaptation keeps upstream keymap grammar and reports effective physical conflicts as release-visible keymap warnings. Windows ships its own default chord for every action the fold would park on bare Ctrl (`WindowsDefaultChords`), so two default conflicts remain: Ctrl+Alt+Up (`previous_session` over `previous_attention_session`) and Ctrl+Alt+Down (`next_session` over `next_attention_session`). This changes only Windows input routing and diagnostics; builtin names, configuration parsing, control commands, and wire responses are unchanged.

- **S4 renderer settings and Windows composition.** One immutable snapshot maps the existing app settings into page-global xterm options and applies them to every current and future pane without recreating ConPTY sessions. It covers font family and size, the current Windows base palette, cursor defaults, scroll sensitivity, scrollback, right-click paste, and screen-reader mode. Named theme resolution remains in the D3 live theme catalog; S4 removes bridge-local color literals without implementing `theme.set` early. `backgroundOpacity` stays a window-composition setting: opaque windows use Mica, translucent windows use a transparent WebView2 background plus Desktop Acrylic when blur is nonzero, and no system backdrop when blur is zero. Windows App SDK controls the acrylic blur strength, so the persisted 0..100 value gates blur but does not map to an exact radius. `config.reload` uses the shared settings sequence described below, updates existing/future panes and sidebar typography/status styling, and clears per-session font zoom as upstream explicit reload does. The optional WebGL addon is capability-detected but is not vendored in this pin; xterm's built-in renderer remains the tested fallback. Live tests verify Unicode, IME composition, selection, and screen-reader DOM behavior. No settings, control-command, tree, or wire field names changed.

- **Safe settings updates and shared application.** Startup keeps the existing default-settings recovery, including the seeded `agterm` theme for a missing file. Strict reads, edits, saves, and explicit reloads reject malformed or unreadable files instead of replacing them with defaults. A draft update compares its original snapshot with the latest file, merges unrelated external edits, and preserves unknown fields, unknown interface-element names, and settings outside that draft. Conflicting edits to the same field require an explicit reload; `theme`, `darkTheme`, and `followSystemAppearance` form one conflict group. Store instances writing the same path share an in-process lock. Each write uses a unique temporary file, rechecks the file revision, then replaces the destination atomically. An external editor does not honor that lock, so the revision check and rename are not a filesystem compare-and-swap against arbitrary external writers.

- **Settings save and apply failures.** One application-owned coordinator serializes writes and reloads, publishes the committed snapshot and apply/error state, and awaits every window's host and UI application. A newly opened window receives the latest snapshot. Save or read failure retains the previous snapshot; a saved file whose application fails stays saved, other windows are still attempted, and an explicit reload retries application. Failures reach the existing app InfoBar and diagnostics. Changing `configDirectory` swaps the keymap store and uses the existing reload event to refresh the hotkey manifest and shortcut diagnostics. Applied theme slots also update `theme.list` readback. Theme commands replay their intent over the latest file rather than saving a stale window record; if a theme save fails, the coordinator restores readback and presentation from the last committed snapshot before accepting another update. `config.reload` keeps its asynchronous `ok` response and `count: 0`; the coordinator, not that response, reports completion or failure. No wire command, builtin action, or settings field is added. `restoreRunningCommand` remains restart-only. The deferred inactive-window sidebar, dock-bounce, and auto-follow settings gain no runtime behavior.

- **Settings window (Windows UI).** The pinned upstream Settings scene becomes one app-owned WinUI window with the same six tabs: General, Appearance, Interface, Notifications, Agent Status, and Key Mapping. The title-bar button and Help > Settings open it. Alt+, follows the port's bare-command-to-Alt defaults; Ctrl+, also works, as in Windows Terminal and VS Code. Either opener yields to an explicit builtin override or custom-command binding, including a leader's first chord. They are app gestures, not new `BuiltinAction` values or wire commands. Every open selects General and raises the existing window; its tab and geometry are not persisted, and closing the last terminal closes Settings. Key Mapping reuses the shortcut catalog, search, conflicts, and diagnostics from the existing overlay.

- **Settings chrome.** Upstream Settings follows macOS system appearance. The Windows window instead uses the current global agterm theme's light/dark chrome, through the same `LiveThemeSettings.Resolve` / `UseDarkChrome` computation as terminal windows. Follow-system mode resolves the active global theme slot against Windows appearance. Workspace themes do not affect Settings, and the window uses neutral Windows controls and Mica rather than the terminal palette. The content and native title bar update after shared settings application (including theme commands and config reload) and Windows appearance changes.

- **Settings controls and Windows adaptations.** Changes use the shared safe editor and apply sequence above. Failed writes retain the draft with Retry and Reload actions; external same-field edits require reload, and unrelated edits merge. Use default removes an override rather than writing a default value. ## Shell integration (cwd reporting)

Upstream never implements this. libghostty injects its own shell integration into bash, zsh, fish and elvish, so OSC 7 arrives for free, and agterm only turns parts of it off (`shell-integration-features = no-cursor,no-title` in `ghostty-defaults.conf`). A WebView2/xterm.js surface has no injector, and no Windows shell reports its working directory on its own.

Without a report `Session.CurrentCwd` stays null forever, `EffectiveCwd` falls back to `InitialCwd`, and every restored session reopens at the directory it was first created in. The port therefore ships its own per-shell scripts in `src/AgTerm.Xterm/Integration/`:

| Shell | Script | Attached as | Reports |
| --- | --- | --- | --- |
| `pwsh.exe`, `powershell.exe` | `integration.ps1` | `-NoExit -Command ". ([scriptblock]::Create([IO.File]::ReadAllText('<script>')))"` | OSC 9;9, OSC 7777 (readline marker) |
| `cmd.exe` | `integration.cmd` | `/k call "<script>"` | OSC 9;9 |
| `bash.exe` (Git Bash) | `integration.bash` | `--rcfile <script> -i` | OSC 7 |

`wsl.exe` is excluded deliberately: it runs another OS, where a Windows script path does not exist and a reported path would be a `/mnt/c` location this side cannot spawn in. Any other shell is `ShellKind.Unsupported` — spawned exactly as before, with no cwd tracking rather than an error.

Constraints the implementation is pinned to, each of which was a real failure first:

- **The PowerShell script is loaded as text, not as a file.** Windows PowerShell 5.1 on a client Windows treats an undefined execution policy as `Restricted` and refuses `. '<script>'` with `PSSecurityException`; pwsh 7 treats it as `RemoteSigned`, which is why the file form only ever failed in 5.1. Execution policy checks script files only, so `[scriptblock]::Create` over the file's text runs under any policy. `-ExecutionPolicy Bypass` would also work, but it would lift the policy for everything the user runs in that shell. `PowerShellReadlineIntegrationTests` starts the shells with the same command.

- **Only a bare shell argv is rewritten.** `LiveControlHost.CaptureRequest` puts a user's own program in the same `argv` for `session.new --command`. Injecting there would replace that program with a shell and break restore, so `ShellIntegration.Inject` rewrites a single-element argv naming a known shell and returns everything else untouched.
- **The existing prompt is wrapped, not replaced.** `$function:prompt` is captured as a value (resolving it by name inside the wrapper would recurse), and the user's prompt still renders. Verified against a live Oh My Posh profile. `integration.bash` appends to `PROMPT_COMMAND` for the same reason, and re-sources `~/.bashrc` because `--rcfile` replaces it.
- **cmd gets `call` and the script path as separate argv items.** The spawn builds its command line with the MSVCRT quoting rules, which escape an embedded quote as `\"`. cmd does not parse its line with those rules: `/k` strips only the outer quotes, so the single argument `call "<script>"` reached it as `call \"<script>\"` and failed with `'\"…\integration.cmd\"' is not recognized`. As separate items the path is quoted whole, and the line is `/k call "<script>"`. `ShellIntegrationTests` runs the result against a real `cmd.exe` from a path with spaces and a `#`.
- **No script emits OSC 0/1/2.** `Session.DisplayName` prefers `oscTitle` over the cwd basename, so an auto-title would overwrite every sidebar row with a path — the same reason upstream sets `no-title`.
- **The OSC 7 URI needs three slashes and a literal colon.** `file:///C:/git/x` parses; `file://C%3A%5Cx` puts the drive letter in the host position and is rejected, and `file:///C%3A/x` yields a leading-slash path. Measured against `CwdReport.Parse`.
- **The scripts must stay real files, and are found via the exe path.** They are marked `ExcludeFromSingleFile`, because a `PublishSingleFile` bundle would hide them from the shell that is handed their path. `ShellIntegration.ResolveScriptDirectory` therefore tries `Environment.ProcessPath`'s directory BEFORE `AppContext.BaseDirectory`: in this app's single-file publish the two differ — `BaseDirectory` is the bundle extraction directory under `%TEMP%\.net\agterm-win\<hash>\`, while the excluded scripts stay beside the exe. A plain console single-file app reports the two as equal, so this only reproduces in the real app. Existence is checked, so a layout missing the scripts degrades to a plain shell.

A `cd` still does not trigger a disk write (spec line 81: reports arrive on every prompt, so only structural mutations save). The directory survives an ordinary quit because window close and `LiveApplicationHost.Dispose` both save; a hard kill still loses cwd changes made since the last structural mutation.

### PowerShell readline marker (OSC 7777)

`integration.ps1` also wraps `PSConsoleHostReadLine`, the function the PowerShell host calls to read a command line, if it exists. Before each read it writes `ESC]7777;agterm-readline=1` and, when PSReadLine binds `Paste` to Shift+Insert or Ctrl+V, `;paste=shift-insert` or `;paste=ctrl-v`. A `finally` block writes `ESC]7777;agterm-readline=0` once the read ends. The bindings are read on every prompt, so a change made with `Set-PSReadLineKeyHandler` or `-EditMode` applies at the next prompt. The page uses the marker to send paste keys to PSReadLine (see Clipboard chords) and to send Ctrl+letter keys with the Latin letter (see Letter keys on non-Latin layouts).

- **This is a private sequence, not part of the control API.** Only this app's page reads it. 7777 is not used by xterm.js or the common OSC sets (7, 8, 9, 52, 133, 633, 777, 1337, 5522). Unknown payloads change nothing.
- **Only a pane the app started with the integration listens.** `ShellIntegration.ReportsReadline` is true only for the exact argv `Inject` builds for pwsh and powershell, and `TerminalPane.OpenAsync` passes the result to `openPane` as `readlineMarker`. In cmd, Git Bash, WSL, a `--command` pane or an overlay, a program that writes the sequence only writes output.
- **The wrapper keeps `$?`.** PSReadLine's own function reads `$?` first and uses it, for example for the `-PromptText` error color. The wrapper reads `$?` in its first statement; after a failed command it runs `Write-Error 'agterm' -ErrorAction Ignore` right before it calls the original, so the original sees False again. `-ErrorAction Ignore` keeps the error out of `$Error`. `PowerShellReadlineIntegrationTests` checks this with a real Windows PowerShell 5.1 and pwsh.
- **The marker arrives with the output, so it can be late.** After Enter, until `agterm-readline=0` arrives, a paste key still goes in the PSReadLine form, to the command that just started; a command that reads input gets that key instead of the text, and a non-Latin Ctrl+letter key carries the Latin letter. After a command ends, until `agterm-readline=1` arrives, a paste is typed in as before. Each window is one ConPTY output frame plus the pipe and the WebView2 hop.
- **Output in the pane can contain the marker.** `cat` of a file or a remote host over `ssh` can write it. Then paste keys send PSReadLine's paste key to that program, and non-Latin Ctrl+letter keys carry the Latin letter, until the next prompt sends the correct value. No data leaves the machine, and `agtermctl session paste` still pastes. A nonce would need a new `AGTERM_*` variable or argv, and a program in the pane can read both, so there is none.

## Terminal links

**Upstream behavior and Windows mapping.** Ctrl+left-click is the Windows counterpart of upstream's Cmd+left-click. The classifier follows [LinkPolicy at the parity pin `7df70fe`](https://github.com/umputun/agterm/blob/7df70fe/agtermCore/Sources/agtermCore/LinkPolicy.swift): `http`, `https`, `mailto`, and `ftp` open through the system handler; local `file:` URLs reveal their target; other schemes and schemeless POSIX or relative paths do nothing. A local file authority is empty, `localhost`, or this machine's name, normalized without DNS lookup. A terminal file URL must identify a fully qualified Windows drive path, such as `file:///C:/Users/me/report.txt`; it never borrows the app's current drive. Unlike macOS, `C:\net`, `C:\Network`, and `C:\home` are ordinary directories, not automount roots. Existing HUD markdown eligibility is unchanged.

OSC 8 targets take precedence over detected text, including when the visible label is another URL. The default Ghostty [URL/path matcher](https://github.com/ghostty-org/ghostty/blob/4dcb09ada0c0909717d92547623b26eafa50ca8a/src/config/url.zig) at agterm's pinned Ghostty revision also highlights POSIX paths, but agterm's classifier ignores those schemeless targets. Windows uses xterm.js's OSC 8 handler and a custom link provider, not a browser navigation or a web-links addon. Detection joins soft-wrapped buffer rows, maps Unicode characters to terminal cells, and never joins hard newlines. Ordinary mouse clicks and text selection remain terminal gestures. Ctrl+click resolves the buffer cell on both press and release, independently of hover state. Both must identify the same target in the same cell; small pointer movements within that cell are allowed. A link gesture consumes the press and release rather than sending a mouse report to the foreground program.

**User-requested Windows addition.** Revealing a plain absolute drive path, such as `C:\Users\me\scratchpad\notes-2026-10-22.txt`, is a divergence requested by the user: upstream highlights plain paths but does not reveal them. Both slash styles work. Double quotes, single quotes, or backticks delimit paths containing spaces. An unquoted path stops at two or more spaces, a tab, a quote/formatting delimiter, or the logical line's end. Trailing padding and sentence punctuation are excluded. A single space remains part of the path, so `C:\Program Files\x` works without quotes. The host first checks the full detected path. If an unquoted detected path does not exist, the host tries shorter paths cut at whitespace boundaries, longest first. It reveals the longest existing candidate. Quoted paths, OSC 8 targets, and file URLs do not use shorter candidates.

**Reveal and rejection rules.** Explorer selects an existing file or directory with `/select,`; it never opens the file's associated application. An executable, script, or shortcut is also only selected. The host validates the target again and starts Explorer from its full path in the Windows directory, without a command shell. Classification is lexical and does not resolve symlinks or access the filesystem. The host validates each candidate before checking its existence. Disk checks run off the UI thread. If no accepted candidate exists, the app shows a `Path not found: C:\...` InfoBar notice with the full detected target. A missing path is not a task fault. Launcher failures use the same InfoBar. UNC paths, remote file authorities, device/extended namespaces, drive-relative and root-relative paths, NTFS alternate streams, reserved device names, malformed escapes, and invalid/control characters are rejected before any existence check. File URL paths are percent-decoded before validation. Opened URLs and file URLs must be printable ASCII as written; encode spaces and non-ASCII characters in URLs. Plain drive paths can contain Unicode and spaces.

No control command, CLI flag, environment variable, keymap action, or setting is added. Upstream HEAD `e9d3baa` adds browser/session-overlay routing through `linkOpenMode`; this change does not adopt that feature.

## WebView2 process death

Upstream has no analogue. libghostty renders in the app's own process, so there is no renderer that can die while the app keeps running. This port draws every pane in a WebView2, which runs its terminals in separate browser processes, and those processes can exit on their own.

What made this worth handling: the `CoreWebView2` object stays alive after its process dies. `WinRtScriptHost` captures it once at boot (`MainWindow.BootPageAsync`) and `_pageTask` is a `Task` that completes once, so nothing re-reads either. Every later `ExecuteScriptAsync` throws. The observed result was an app that ran for two days, lost its renderer, and then reported "Terminal failed to start" on all five restored sessions, with no statement of the real cause and no recovery short of a restart.

`CoreWebView2.ProcessFailed` is subscribed right after `EnsureCoreWebView2Async`, so it covers failures after a successful init. Initialization exceptions and a page that does not post its ready message within 12 seconds both show a fatal failure InfoBar with a Reload button. The app writes the full initialization exception, including inner exceptions and stack traces, to its existing `Trace` output. There is no automatic retry.

- **Only some kinds take the page down.** `WebViewProcessFailure.IsFatal` treats `BrowserProcessExited`, `RenderProcessExited` and `RenderProcessUnresponsive` as fatal. `GpuProcessExited`, `UtilityProcessExited`, `SandboxHelperProcessExited`, the two PPAPI kinds and `UnknownProcessExited` leave the page running, and WebView2 recovers those processes itself. `FrameRenderProcessExited` covers an out-of-process iframe, which this page does not host.
- **An unrecognized kind reads as survivable.** A newer runtime can name a kind this build does not know. Claiming the terminals are gone while they still work is the worse error.
- **The kind arrives as its enum name.** `AgTerm.Xterm` has no WinUI or WebView2 reference, and the mapping is the part worth testing without a browser, so `MainWindow` passes `ProcessFailedKind.ToString()`.
- **The fatal notice holds the banner.** `FailureBanner` is one `InfoBar` and the newest notice replaces the last, so the per-session spawn failures that follow a dead renderer would bury the one notice that explains them. `FailureNoticeGate` drops every notice after a fatal one, including a repeat of the fatal notice itself, because WebView2 can raise `ProcessFailed` more than once.

Reload replaces only the WebView2 and terminal page in the window where the button was pressed. The application pipe, other windows, detached quick panel, session identities, selection, and workspace state remain. Once the new page is ready, that window replaces its page-bound main, split and scratch panes and realizes their sessions again. Existing ConPTY children in that window are stopped and new processes start: the current output pump and terminal input handlers bind each child to the old renderer, so they cannot be moved to a new page. Reload closes active overlays through the normal close path instead of running their one-shot commands again. A client polling `session.overlay.result` receives `no overlay result` and stops waiting if the overlay had not exited before the reload; an exit status already recorded by the close path remains available. If page initialization fails again, the button stays available on the new failure notice.

## Keyboard protocol (kitty CSI u, win32-input-mode)

Upstream does not carry this. agterm draws on Ghostty, which implements the kitty keyboard protocol itself, so an app running inside upstream agterm can ask for CSI u encoding and get it. Here the engine is xterm.js, and 6.0.0 has no support for the protocol at all: every key arrives at the pty in its legacy form. Enter and Shift+Enter are both CR, and nothing downstream can tell them apart.

That is a feature gap in the engine, not a parity divergence: the control API, the keymap grammar and the builtin actions are untouched. It is recorded here because the fix pins a prerelease.

- **The core runs on a 6.1.0 beta.** `vtExtensions` (`kittyKeyboard`, `win32InputMode`) is the option that carries it, and 6.1.0-beta is the first release to have it. `src/AgTerm.Xterm/Assets/vendor/MANIFEST.md` holds the pins and explains why the addons sit at a lower beta number than the core.
- **Both extensions are off by default in the engine, and both are enabled here.** `buildTerminalOptions` sets them for every pane. `win32InputMode` (`DECSET 9001`) is the ConPTY-native way to report full key events and helps TUI input generally.
- **The kitty protocol outranks win32-input-mode here, and the engine does the opposite.** `KeyboardService.evaluateKeyDown` checks win32-input-mode first and returns before the kitty path, so an app that enables both gets win32 key records. Claude Code enables both: it writes `DECSET 9001` at startup and then `CSI > 5 u`. Measured from the real `claude.exe` through a pseudoconsole, the first bytes out are `ESC[?9001h`, then `ESC[<u ESC[>5u ESC[>4;2m`. Shift+Enter then left as `ESC[13;28;13;1;16;1_`, which Claude Code does not read as Shift+Enter, so it submitted the prompt instead of inserting a newline. Ctrl+Enter worked throughout, because it survives as a win32 record the app does understand - that asymmetry is what identifies this bug. `openPane` watches the kitty push and pop and clears the `win32InputMode` option while a request is in effect, so the pane encodes what the app asked for. The mode itself stays set: `DECSET 9001` is the app's, not ours, and the option is what the engine consults. `XtermPageLiveTests.Popping_the_kitty_stack_gives_win32_input_mode_back` pins the restore.
- **An app that never asks keeps the old encoding.** The protocol is opt-in over the wire: the engine answers `CSI ? u`, tracks the stack pushed by `CSI > flags u` and popped by `CSI < n u`, and reports CSI u only while a request is in effect. Enabling the option changes nothing for a program that does not use it. `XtermPageLiveTests.Shift_enter_reports_kitty_csi_u_while_the_keyboard_protocol_is_pushed` pins all three states: CR before the push, `ESC [13;2u` for Shift+Enter while pushed, CR again after the pop.
- **Host chord interception runs before keyboard encoding.** `attachCustomKeyEventHandler` resolves letter chords from the typed Latin letter or the physical key on a non-Latin layout. The keymap still decides which chords reach the pty, regardless of the active keyboard protocol.
- **Shift+Enter under modifyOtherKeys, for Copilot CLI.** Copilot CLI does not push the kitty protocol. At startup it writes `ESC[>4;2m` (modifyOtherKeys level 2) and the kitty query `ESC[?u`. ConPTY does not answer the query (see "Terminal identification" below), so Copilot CLI stays on legacy input. xterm.js does not implement modifyOtherKeys, so Shift+Enter left as a win32 Enter record and Copilot CLI submitted the prompt. Measured with the real `copilot` 1.0.105 through a pseudoconsole: the win32 Shift+Enter record `ESC[13;28;13;1;16;1_` submits; `ESC[27;2;13~`, `ESC[13;2u` and `ESC CR` insert a newline; the win32 Ctrl+Enter record inserts a newline too. `openPane` tracks `CSI > 4 ; n m`: `n` of 0, or no `n`, turns it off, and Copilot CLI writes `ESC[>4;0m` on exit. While the level is 1 or more and no kitty flags are pushed, the pane sends Shift+Enter (without Ctrl, Alt or Meta) as `ESC[27;2;13~`, the form xterm sends under modifyOtherKeys, and sends no release record for it. No other key changes. A pushed kitty protocol still decides the encoding, so Claude Code, which sends both, gets `ESC[13;2u` as before. A program that exits without turning the mode off leaves Shift+Enter in this form until the next `CSI > 4 m`. `XtermPageLiveTests.Shift_enter_reports_modify_other_keys_form_while_the_mode_is_on` pins the states.

Claude Code is the case that motivated this: its newline-without-submit binding needs Shift+Enter to be distinguishable from Enter, and `claude /terminal-setup` cannot help, since it writes per-terminal config for a fixed list of known terminals and has no entry for this app. Supporting the protocol is not sufficient on its own, because the request has to come from the program: see the next section.

## Saving a file while another process holds it

Every stored file is written to a temp file in the same directory and renamed over the destination, so a crashed write leaves the old file rather than half of the new one. On Windows that rename fails with `UnauthorizedAccessException` ("Access to the path is denied") while any other process holds the destination open, even for reading: a reader with `FileShare.Read` is enough, measured directly.

Nothing in this app opens those files twice. The holder is outside it, a virus scanner or the search indexer opening a file for a moment right after it is written, so the lock lasts a moment and the next attempt succeeds. `LiveApplicationHost.SaveIndexLocked` threw out of a test run that way, and the same pattern sat in `PersistenceStore`, `RecentClosed` and `SettingsStore`.

`AtomicFile.Replace` retries the rename for 2 seconds, backing off from 10ms to 100ms, and rethrows if the lock outlasts that. A caller that could not store its state has to hear about it: `RecentClosed` already swallows these exceptions by design (upstream does too), while the other three propagate.

## Clipboard chords

Upstream has no clipboard entry among the 41 builtin actions, and `parity/surface.json` confirms it: copy and paste exist only as the control commands `session.copy` and `session.paste`. On macOS the chords belong to Ghostty, which agterm runs inside. Here there is no such host, so a pane received no clipboard chord at all: Ctrl+V, Ctrl+Shift+C/V, Ctrl+Insert and Shift+Insert were dropped, and only Ctrl+C did anything, by sending 0x03.

The chords are added in the pane, not in the keymap. Adding builtin actions would change the parity surface; the keymap grammar also has no `insert` key, so two of these chords cannot be written in it. They are handled in `openPane` instead, after the keymap, so a user binding on the same chord still wins.

- **Ctrl+C copies only when there is a selection.** With nothing selected it sends 0x03 in the default keyboard mode, so interrupting a running program keeps working. `XtermPageLiveTests.Ctrl_c_without_a_selection_still_interrupts` pins that half.
- **Ctrl+Shift+C and Ctrl+Insert copy only when there is a selection.** With nothing selected they do nothing and send no input to the terminal. Ctrl+V, Ctrl+Shift+V and Shift+Insert request a paste.
- **The letter chords also work on non-Latin layouts.** When the typed key is not an ASCII letter and Alt is not held, the pane uses the physical `KeyC` or `KeyV` position. With no selection, xterm encodes Ctrl+C for the active keyboard mode.
- **The host writes the clipboard, the page does not.** `navigator.clipboard.writeText` fails with `NotAllowedError` without a user gesture, and a key event dispatched by the engine does not count as one. Measured in the live WebView2: the page is a secure context and the API is present, and the write is still refused. A copy posts `copyRequested` with the selected text and `MainWindow` writes it, which mirrors the clipboard read that right-click paste already used.
- **While PSReadLine reads a command line, a paste goes to PSReadLine.** The app types a paste in as ordinary input, so PSReadLine records one undo step per character and runs each line at its newline. Its own `Paste` function reads the clipboard and inserts the text as one edit. So when the pane has the readline marker (see Shell integration), Ctrl+V, Ctrl+Shift+V, Shift+Insert and right-click send PSReadLine's paste key instead of requesting a paste. With `paste=shift-insert` the pane sends `ESC[2;2~`; ConPTY reads it in every keyboard mode. With `paste=ctrl-v` (Vi mode) it sends the win32-input-mode press and release records of Ctrl+V with the character `v`, and only while win32-input-mode encodes keys. The pane sends the release itself and xterm sends none. Without a `paste` part, after `agterm-readline=0`, or in any other pane, the app pastes as before. `agtermctl session paste` always types the text in.
- **A multi-line paste into PowerShell no longer runs line by line.** PSReadLine inserts all lines into the edit buffer, and nothing runs until Enter; then all lines run as one input. Classic conhost and Windows Terminal do the same with Ctrl+V in PowerShell. To run the lines as they arrive, use `agtermctl session paste`.

## Letter keys on non-Latin layouts

The pane resolves built-in and custom keymap chords from the typed ASCII letter when one exists, otherwise from the physical `KeyboardEvent.code` (`KeyF` to `f`). Alt+F opens search and other app chords match on a Russian layout. A user `map` binding still wins where the host gives it priority. On a Latin layout such as Dvorak, the typed letter wins over the physical QWERTY position. Ctrl+Alt does not use the physical-letter fallback, so AltGr characters do not trigger app chords. A digit or punctuation key is named by its unshifted US key, as keymap.conf writes it (`shift+9`, not `(`): the pane uses the key's `KeyboardEvent.code` position whatever character Shift or the layout makes it type, so Ctrl+Shift+9 matches `ctrl+shift+9`, and on a Russian layout Alt+`ю` matches `alt+.` and Ctrl+/ (which types `.`) matches `ctrl+/`. A key that types a Latin letter keeps the letter, as on Dvorak, and Ctrl+Alt keeps the typed character here too. The window names the keys the same way while the focus is outside the terminal: the OEM virtual keys take their US characters (they follow the US positions on the US and Cyrillic layouts), and the numpad plus and minus are `+` and `-`. A chord on `+` without Shift, the Windows default `alt++` for `increase_font_size`, also fires from the equals key with or without Shift, after any binding on the equals key itself, because the keymap can only write plus as a character that sits on that key; upstream's `cmd++` fires from Cmd+= the same way. A custom command bound to Alt+= keeps that press.

If a non-Latin Ctrl+letter key is not consumed by a chord or the clipboard handler, the pane gives xterm the corresponding Latin key before encoding. Ctrl+F on a Russian layout therefore sends 0x06 in legacy mode, and the same output as Latin Ctrl+F in kitty and win32-input modes. Plain Cyrillic text and Shift+letter remain typed characters; the clipboard handler and agent status-clear rules stay in place.

That is not enough for PSReadLine. It names a key whose character is a control character through the keyboard layout, so the win32-input-mode record of Ctrl+Z (character 0x1a) reads as Ctrl+я on Russian, and `Undo` does not run. A record with the character `z` reads as Ctrl+z on any layout. So while the readline marker says PSReadLine reads input (see Shell integration), and win32-input-mode encodes keys, the pane sends Ctrl+letter (no Shift, Alt or Meta) on a non-Latin layout as the record with the lowercase Latin letter: `ESC[90;44;122;1;8;1_` for Ctrl+Z. The other fields are what xterm sends for Latin Ctrl+Z. The pane also sends the matching release record, and xterm sends none. It forgets a held key when the terminal loses focus, and a new press of the key replaces it.

- **Ctrl+Shift+letter is not changed.** xterm's record of it (control character plus Shift) matches a `Ctrl+Shift+letter` binding on both layouts, and a record with the uppercase letter does not on Russian.
- **Other keys that PSReadLine names from the typed character still break on Russian.** Alt+letter: `Alt+d` (KillWord), and in pwsh 7 `Alt+a` (SelectCommandArgument) and `Alt+h` (ShowParameterHelp) arrive as `Alt+в`, `Alt+ф`, `Alt+р`. Ctrl with a punctuation key that types a letter on Russian: `Ctrl+]` (GotoBrace) arrives as `Ctrl+ъ`.

## Agent status on terminal input

On macOS a terminal surface calls the status-clear handler from `keyDown`; a modifier-only press takes the separate `flagsChanged` path. On Windows each xterm pane posts `userKeystroke` only after the pane's handler has left a non-modifier key for xterm. A bare Control, Shift, Alt, Meta, AltGraph, or lock-key press does not clear the status before an app chord. App chords and clipboard shortcuts consumed by the page do not clear a status either. In particular, Ctrl+C with a selection copies without clearing an active status, while Ctrl+C without a selection reaches the terminal and clears it. The browser supplies `KeyboardEvent.code` for the physical C position and `key` for the produced character: bare Ctrl+C works on Cyrillic and Latin layouts, but Dvorak Ctrl+J at `KeyC` does not count as an interrupt. Escape interrupts with any modifiers. The live host resolves main, split, and scratch from the current surface when it handles the message, so a promoted split clears a left-pane status. The WebView2 thread sends the key event to the host's store gate without waiting for it; no control command or wire field changes.

## Terminal identification for spawned shells

Upstream needs none of this. agterm runs on Ghostty, so a child process reads Ghostty's own `TERM=xterm-ghostty` and `TERM_PROGRAM=ghostty` and knows what it is talking to. Here the children are spawned by a WinUI app, and the app declared nothing: `AGTERM_PANE_ID` was the only variable added, so everything else was inherited from whatever started agterm-win. Launched from an IDE terminal, the shell reported that IDE. `TerminalIdentity` declares the identification, and `ConPtySession.RemoveEnvironment` can drop an inherited variable instead of only overwriting it.

- **`TERM` is declared as `xterm-256color`.** What xterm.js implements. Inheriting left it describing a different emulator, or missing entirely when the app was launched from Explorer.
- **`TERM_PROGRAM` is declared as `ghostty`.** See below: this is an allowlist key, not a description.
- **`TERM_PROGRAM_VERSION` and `WT_SESSION` are removed.** `TERM_PROGRAM_VERSION` has no declared value to beat it with, so an inherited version would be read as this terminal's. `WT_SESSION` is read later in the same detection chain and reinstates the Windows Terminal path on its own.

### The terminal name is an allowlist key

Programs gate keyboard features on the terminal name, and Claude Code is the case this port had to satisfy: without the kitty keyboard protocol, Enter and Shift+Enter both reach the pty as CR and newline-without-submit cannot work.

It settles `extendedKeys` from the environment only for a name on a fixed list - `iTerm.app`, `kitty`, `WezTerm`, `ghostty`, `tmux`, `windows-terminal`, `WarpTerminal` - and pushes the protocol (`CSI > 5 u`) on the same test. Two findings, both measured rather than reasoned:

**`windows-terminal` is the one entry that costs the feature.** For that name specifically, Claude Code additionally requires a CONFIRMED reply to the kitty query `CSI ? u`. A default does not count, only an answer that came back. That answer never arrives, and not because of the engine. ConPTY answers terminal queries itself instead of forwarding them:

| Query | Answer when fed straight into xterm.js | Answer through ConPTY |
|---|---|---|
| `CSI > 0 q` (XTVERSION) | `DCS >\|xterm.js(6.1.0-beta.304) ST` | none |
| `CSI ? u` (kitty) | `CSI ? 0 u` | none |
| `CSI c` (primary DA) | `CSI ? 1 ; 2 c` | `CSI ? 61 ; 6 ; 7 ; 21 ; 22 ; 23 ; 24 ; 28 ; 32 ; 42 c` |

The third row is the tell: a reply arrives, but it is conhost's signature, not xterm.js's. conhost answers what it knows and silently swallows what it does not. `PSEUDOCONSOLE_PASSTHROUGH_MODE` (flag `0x8`) was tried on build 26200 and changed none of this.

**Declaring no name is not an option.** The detection chain ends with `return process.env.TERM`, so with `TERM_PROGRAM` unset the terminal was named `xterm-256color`, which is not on the list, and `extendedKeys` went off entirely - worse than the Windows Terminal claim it replaced.

That leaves the list. `ghostty` is the entry this port can carry: the others are gated on a version string that would have to be published and kept plausible as those terminals release, and `windows-terminal` is the dead end above.

Upstream sets `TERM_PROGRAM=agterm` and `TERM_PROGRAM_VERSION=<agterm version>` in its session environment. This port keeps `ghostty` for the reason above, does not set a version, and removes an inherited one for the reason in the list above.

This is a claim about behaviour, not provenance, and it is narrower than it looks. The protocol stays opt-in over the wire: the engine reports `CSI u` only while an application has pushed the stack, so a program that never asks keeps the legacy encoding. Capabilities that are probe-confirmed rather than name-granted - kitty graphics, pixel mouse - stay off on their own, because the probe gets no reply through ConPTY.

The engine side is not in question: feeding either `CSI > 5 u` (what Claude Code sends) or `CSI > 1 u` into a live pane makes a following Shift+Enter arrive as `ESC [13;2u` instead of CR. Both are covered by live tests.

What the name gives up is one performance optimization that was tied to `WT_SESSION`: Claude Code skipped its `DECSTBM` scrolling-region path for a Windows terminal session and repainted more instead. Correct either way.

If a future program needs something else from the name, the question to ask first is whether it queries the terminal to confirm what the name claims. Any capability confirmed by a query hits the same wall, until ConPTY forwards queries or this port answers them itself.

## Session environment

Every shell the app spawns gets `AGTERM_*` variables, so a script or an agent in it can tell it runs in agterm-win and can reach the app. `SurfaceEnvironment` in `AgTerm.Core` builds them. It ports upstream `SurfaceEnvironment` at the pin: the same names, the same conditions, UUIDs in upper case.

- **Main, split and scratch** get `AGTERM_ENABLED=1`, `AGTERM_SESSION_ID`, `AGTERM_WINDOW_ID`, `AGTERM_WORKSPACE_ID`, `AGTERM_SOCKET`, `AGTERM_PANE` (`left`, `right` or `scratch`) and `AGTERM_PANE_ID` (the spawn token).
- **The overlay** gets the session set without `AGTERM_PANE` and `AGTERM_PANE_ID`. It is a session surface, not a pane.
- **The quick terminal** gets `AGTERM_ENABLED` and `AGTERM_SOCKET` only. It belongs to the app, with no window, session, workspace or pane identifiers.
- `AGTERM_WORKSPACE_ID` and `AGTERM_SOCKET` are left out when there is no value, as upstream does.

**`AGTERM_SOCKET` holds a socket path, not a pipe name.** The value is `<state dir>\agterm.sock`, the path the pipe name is derived from (see "Transport: named pipe" in Phase 2). `agtermctl` derives the pipe from `--socket` the same way, so `agtermctl <command> --socket "$env:AGTERM_SOCKET"` reaches the app that started the shell. When the `AGTERM_CONTROL_SOCKET` override is set, the app listens on a literal pipe name, no path derives to it, and `AGTERM_SOCKET` is not set.

**Inherited values are removed.** Upstream is started by launchd, so a foreign `AGTERM_*` value never reaches it. This port can be started from a pane of another instance. Then the app process carries that instance's values, and a shell that inherits them would talk to the wrong app. Every surface spawn removes all seven names before it sets its own, and custom commands remove all seven and set none.

**The shell integration scripts gate on `AGTERM_ENABLED`.** They used to gate on `AGTERM_PANE_ID`. The quick terminal sources the integration too, and it has no pane id now.

## Product name: agterm-win where a user sees it, agterm on the wire

This port is an independent product, not a build of upstream, so it never presents itself as "agterm". Everything a user sees carries `agterm-win` (`ProductIdentity.Name` in `AgTerm.Xterm`): the window caption (`agterm-win`, `<session> — agterm-win`, `Dashboard — agterm-win`), the title bar of an empty window, the fallback title of the in-window notification, the WebView2 process-failure notice, the exe (`agterm-win.exe`, `AssemblyName`), its version resource (`Product`, `AssemblyTitle`, which Task Manager and unpackaged app notifications show), the `app.manifest` assembly identity, and the publish directory (`artifacts\publish\agterm-win\…`). The state directory was already `~\.agterm-win` for the same reason.

Names that are part of the parity contract stay upstream's and are not renamed: `agtermctl`, the `AGTERM_*` environment variables, `{AGT_X}` tokens, the built-in `agterm` theme, and the `agterm-<hash>` pipe name. The `AgTerm.*` project, assembly and namespace prefix is internal. It is not a product name, and no package is published under it.

## Assets must survive packaging, not only a build

The app publishes as a directory, not a single file. `PublishSingleFile` produced a 220 MB exe that unpacked itself into `%TEMP%\.net\AgTerm.App\<bundle id>` before any code ran, and the id is per build, so each new build paid the unpack again and left the previous copy behind (1.4 GB across 8 directories on the development machine). Measured time from launch to window, on the same machine: 34.9 s for the first run of a build and 4.4 s afterwards, against 5.0 s and 1.0 s for a directory. The bundle costs on every launch, not only the first. `agtermctl` publishes with Native AOT as one self-contained native exe, without CLR startup or bundle extraction. It stays beside the app for the existing PATH and hook installers and does not load the app's `hostfxr.dll`. A framework-dependent apphost in that directory would find the app's DLL, treat the directory as a self-contained install and fail with "You must install or update .NET" because there is no `shared\Microsoft.NETCore.App` in it. ARM64 AOT is built and tested in CI; local ARM64 publishing requires the Visual C++ ARM64 tools in addition to the x64 tools and Windows SDK. Commands, JSON options and converters, error strings, and exit codes are unchanged.

The `ExcludeFromSingleFile` and `CopyToPublishDirectory` markings below still apply and are still required. A directory publish makes `AppContext.BaseDirectory` and `Environment.ProcessPath`'s directory the same folder, so both resolutions land in the right place; the markings are what keeps a single-file publish working if it is ever turned back on.

The terminal page is not embedded in the assembly: WebView2 serves it with `MapVirtualHostToFolder(XtermAssets.Directory)`, which resolves to `AppContext.BaseDirectory\Assets` and needs real files on disk. Two separate things have to hold for that, and the published app satisfied neither for a while.

`PublishSingleFile` extracts the bundle to a directory under `%TEMP%\.net\<app>` and points `AppContext.BaseDirectory` there, not at the folder holding the exe. So the assets must stay INSIDE the bundle: marking them `ExcludeFromSingleFile` leaves them beside the exe where nothing looks for them, and the app finds an `Assets` folder containing only the application icon. The page then fails to load and every pane reports `session not realized`, while the sidebar, the control plane and persistence all keep working — the failure looks like a terminal bug rather than a packaging one. `ERR_FILE_NOT_FOUND` in the WebView is the tell.

This is the opposite of `Integration\**`, which must be excluded: those paths are handed to a spawned shell, which cannot read out of a bundle. Same directory, same `None` items, contradictory requirements.

`CopyToPublishDirectory` covers the layouts that are not single-file, where the published project is `AgTerm.App` and a referenced project's `None` items reach a build output through copy-local but stop there.

`XtermAssetsTests.Assets_are_declared_to_follow_a_publish_not_only_a_build` asserts the declaration. It is a weak test — it reads the csproj rather than a published layout — because the existing asset test reads the build output, where the files are always present, so a packaging-only gap is invisible to the suite. Worth remembering for any future run-time file: the question is not whether the build works, but whether the file is reachable from `AppContext.BaseDirectory` in the packaging the user actually runs.

## The WebView2 profile lives with the user's state, not beside the exe

Upstream has no analogue: libghostty renders in the app's own process and writes no browser profile.

WebView2 keeps a profile per application: cache, cookies, local storage and crash metrics. Given no environment it picks the directory itself, and the name it picks is `<exe>.WebView2` next to the executable. For a published build that is the publish directory, which produced two problems.

`publish.proj` starts with `RemoveDir` on the output directory, so a clean publish has to delete a profile written by the last run. WebView2 keeps some of those files memory-mapped past process exit, `EBWebView\CrashpadMetrics-active.pma` among them, so the delete failed and the publish stopped before building anything. The error named a `.pma` file and read as a file-locking problem rather than a layout one.

The second problem is quieter: a successful clean publish wipes the profile, so the app starts cold every time the user rebuilds it.

`MainWindow.BootPageAsync` now creates the environment explicitly with `CreateWithOptionsAsync` and a `userDataFolder` under the app's state dir, `AgTerm.Core.Model.WebViewProfile`. The state dir is the same root as `workspaces.json` and the `windows\` directory, and it honors `%AGTERM_STATE_DIR%`, so two instances pointed at different state dirs do not share one profile. The publish directory then holds the two exes and `Integration\`, and the profile survives a republish.

The resolution lives in `AgTerm.Core` rather than in the window because `AgTerm.App` has no test project. `WebViewProfileDirectoryTests` covers it; the window keeps only the `CreateWithOptionsAsync` call.

A failure to create the directory surfaces through the existing path: the call sits inside `BootPageAsync`, whose task `ReportPageInitializationFailureAsync` already awaits, so it reports an InfoBar rather than crashing.

The WinUI app reaches WebView2 through the Windows App SDK projection, which exposes a narrower surface than the standalone `Microsoft.Web.WebView2` package the test fixture uses. `CoreWebView2Environment.CreateAsync` there takes no arguments, and the only way to name a user data folder is `CreateWithOptionsAsync(browserExecutableFolder, userDataFolder, options)`. Code copied from the fixture, or from Microsoft's WebView2 documentation, will not compile against the app's projection.


## Bringing a window to the front

`window.select` and `pick.open --follow` bring the target window to the front, as upstream does. `Window.Activate` does not do that for a window that is already open: measured with `window.select` from a separate terminal, the window stayed behind and its taskbar button did not flash, even after that terminal had called `AllowSetForegroundWindow(ASFW_ANY)`. `MainWindow.ActivateWindow` therefore also calls `SetForegroundWindow` (`WindowForeground.Raise`).

Windows refuses that call while another application is in front, for example when `agtermctl` runs in a separate terminal and agterm is behind it. Then the window's taskbar button flashes until the user switches to it. Upstream brings agterm in front of other applications, which macOS allows. The routing side does not depend on it: the window is frontmost for routing either way.

## One instance per state directory

macOS keeps one agterm process: a second launch from the Dock, Finder or `open -a agterm` activates the running app. Upstream adds no check of its own; a second process started from the binary takes over the control socket (`ControlServer.start` unlinks and binds it again), and the first one keeps running without it. Windows starts a new process on every launch, and two processes on one state directory overwrite each other's saved workspaces, windows and pane output.

The port registers a Windows App SDK `AppInstance` key derived from the state directory (`SingleInstanceKey`) before XAML starts (`Program.Main`). A second launch on the same directory allows the running process to take the foreground, hands its activation to it, and exits; the running process brings its frontmost window to the front. A process on another `AGTERM_STATE_DIR` has another key and runs beside it. A launch during the seconds a closing last window takes to shut down is handed to that process too, and no window opens; the next launch after it exits starts normally.

## Window position and size after a relaunch

Upstream saves each window's frame when the window closes, under its window id in UserDefaults (`agterm-frame-<uuid>`, `WindowAccessor.swift`), and applies it once when that window opens again, fitted to the displays attached now (`WindowGeometry.bestDisplayIndex` and `constrain`). The port does the same, with three differences:

- The frames live in `<stateDir>\window-frames.json`, keyed by window id, not in a per-user OS store. `AGTERM_STATE_DIR` then isolates them like the other state files, and `windows.json` keeps upstream's shape. An unreadable file reads as no frames.
- A frame is the window's normal bounds in physical pixels plus a `maximized` flag. A window closed maximized opens maximized on the same display, and its restore button returns it to the bounds it had before. macOS has no maximized state, so upstream stores the frame alone. Bounds are taken only while the window is in the normal state; minimized and full screen leave the last normal bounds.
- Full screen is not restored: a window closed in full screen opens with the frame it had before it entered full screen.

The frame is fitted to the display that holds most of it, or the primary display when none does: it shrinks to that display's work area, grows to the 320×240 point minimum `window.resize` uses, and moves fully inside the work area. A new window starts on the primary display, and moving it onto a display with another scale makes Windows rescale it to keep its size in points, so the frame is applied a second time once the window is on its display. A window with no saved frame, such as a new one, opens at the default place. The frame is saved on every close path, including `window.close`; a crash keeps the frame from the last close.

  - `workspaceAddSession`.

## Sidebar workspace icon and session indent

Upstream's sidebar is an `NSOutlineView`: a workspace row has a disclosure triangle and the `square.grid.2x2` icon, and its sessions are indented by `indentationPerLevel = 14`. The port draws the same tree in a flat `ListView`:

- A workspace row shows a four-square icon between the chevron and the name, drawn as a `Path` like the session icons. It takes the row's theme foreground in the `row` style and the secondary text color otherwise.

With 14 px the session icon sits between the chevron and the workspace icon. Only the content moves: the colored background of the `row` style still spans the row. The flagged view has no workspace rows and is not indented.

## Ctrl-Tab session switcher

Upstream's Ctrl-Tab switcher is ported. Hold Ctrl and press Tab to walk the window's most-recently-used sessions, and press Shift+Tab to walk back. Releasing Ctrl selects the highlighted session, and Esc abandons the switch. The state is `SessionSwitcher`, a one-to-one port. The list is frozen when the switch begins and capped at ten inside the visible set. It starts on the previous session, wraps both ways, and needs at least two sessions. The candidates come from `TitleBarState.SwitcherSessions`, captured with each sidebar snapshot, so a switch begins without another trip to the store. A commit selects the session the way the session palette does: it notes user activity, selects the session and focuses the terminal.

- Upstream catches the keys with app-wide `NSEvent` monitors. Here the keyboard is either in the terminal page or in the window's XAML, so both report the same four signals: Ctrl+Tab, Ctrl+Shift+Tab, Esc, and Ctrl's release.
  - The page (`bridge.js`) takes Ctrl+Tab before any other key routing and sends it as a `switcher` message. It then assumes a switch is in progress, so Esc and the Ctrl release (a document `keyup`) are the switcher's until the release or until the host says otherwise (`agterm.setSwitcherActive`). The host corrects the page after every key, for example when fewer than two sessions meant no switch began.
  - The window's `PreviewKeyDown` and `PreviewKeyUp` cover the rest. They run before XAML uses Ctrl+Tab for focus navigation, and they skip a focused WebView2, whose page reports for itself.
- Ctrl+Tab was already reserved: `keymap.conf` cannot bind it (`Chord.IsReservedMonitorChord`).
- The window cannot switch while a palette, a question or the dashboard has the keys. That is the port's reading of upstream's `uiActionsEnabled`. A switch is abandoned when the dashboard opens, as upstream's is, and when the window is deactivated, because the Ctrl release may then land in another window.
- The overlay is drawn in the window below the title bar: a top-centered panel of `name` over `workspace · detail` rows on a light dim, the pick in the accent color. It is never focused and does not take the mouse, so the terminal keeps the keys. Its automation id is `session-switcher`.
- Upstream's Ctrl+1/Ctrl+2 pane shortcuts, its other key monitor, are not part of this port.

## Pane output is restored after a relaunch

Upstream has no analogue: a restored session starts with an empty screen, and the snapshot keeps structure only. The port adds it because VS Code and Windows Terminal do it on Windows, and users expect it there. No command, tree field or wire string changes.

- The setting is `restoreScrollback` in `settings.json`, a Windows-only field. It is on when absent. `"restoreScrollback": false` turns it off. General > Restore saved pane output edits it; `config.reload` also applies a file change.
- At shutdown, before output stops, `LiveControlHost` asks each realized main and split pane for its normal buffer (`bridge.js` `serializeForRestore`, the xterm serialize addon). The alternate screen and terminal modes are left out, so a full-screen program such as vim or Claude Code does not come back as a frozen picture and a mode it set does not leak into the new shell. All panes are asked in parallel, with a 3 second budget; a pane that does not answer is skipped.
- Each pane goes to `<stateDir>\scrollback\<SESSION-UUID>.<left|right>.vt`. The file is taken (read and deleted) when the pane is realized next time, also when the setting is off, so old output does not show up after the setting is turned back on. A crash before the next clean exit does not replay the same output twice. Closing a session, removing its workspace or deleting its window removes its files. Scratch, overlay and quick panes are not saved.
- On realize, `TerminalPane` writes the saved text into xterm, then a dim `-- saved output, new shell below --` line, and only then starts ConPTY. A new pseudoconsole clears the screen at start (`ESC[2J`), which would wipe the restored text. ConPTY is therefore created with `PSEUDOCONSOLE_INHERIT_CURSOR`: it asks for the cursor position (`ESC[6n`), xterm answers through the input pipe, and the shell starts below the restored text without a clear.
- The banner line is part of the buffer at the next shutdown, so each relaunch adds one. The shell process is new: variables, the current command and the PSReadLine state are not restored; PSReadLine history works as before.

## A shell pane stays open when its shell fails

Upstream closes a session as soon as its main shell exits, with any exit code. On Windows a shell is also stopped from outside: an installer that updates PowerShell 7 stops every running `pwsh.exe` first, and every session of every window then closes at once, as if the user had closed them. The port keeps such a pane open, so the user sees that the shell ended and with which code.

- The setting is `closeOnShellExit` in `settings.json`, a Windows-only field. `graceful` (also when absent or any other value) closes the pane when the shell exits with code 0 and keeps it open with any other code. `always` closes it with any code, as upstream does. `never` keeps it open with any code. `config.reload` applies a change to the shells that exit after it.
- It covers the main pane and the split pane, also a split pane promoted to the main pane. Scratch, overlay and quick panes close as before. A session created with `session.new --command` is not a shell pane: it closes or holds by `--wait`, as upstream, so no command, wire field or error string changes.
- A held pane shows a dim `[process exited with code N; press any key to close]` line under its output. The next key the pane passes to xterm closes it the same way the exit would have: a main pane closes the session, or promotes the split; a split pane closes the split. A chord the keymap takes, a mouse click, a focus report and `session.type` do not close it. The session goes to the recently closed list as before, so `reopen_recent` (Ctrl+Shift+T) brings it back.
- An exit code says how the shell ended, not who ended it. In `pwsh`, `exit` exits with 0 also after a failed command, so the user's own `exit` closes the pane. In `cmd.exe`, `exit` without a number exits with the last `ERRORLEVEL`, so after a failed command it keeps the pane open. A process stopped from outside gets the code its stopper chooses; `taskkill /F` gives 1.
- A held pane is saved and restored like any other: after a relaunch it starts a new shell, and with `restoreScrollback` its saved output ends with the banner line.

  - `agtermctl session hud --file` drops a leading UTF-8 BOM before it sends the message. Windows PowerShell 5.1 and Notepad write one, and the server would count it as part of the text.
  - The `--markdown` help says a link opens on a Ctrl+click, where upstream says command-click.
  - Alt+W dismisses a pending control dialog first, then quick only when its panel holds the keyboard (unzoom, then hide). An unfocused pinned panel does not take another window's shortcut. The normal window still dismisses its focused terminal question, session zoom, dashboard, HUD, program overlay and scratch before closing the session. Upstream also dismisses a focused pane overlay after scratch; Windows does not have pane overlays.
  - A link in a markdown HUD opens on Ctrl+click; upstream uses command-click. As upstream, a Ctrl+click anywhere over the panel is consumed with its release, link or not. A terminal question drawn above the HUD and the search bar keep their own clicks.
  - A `file://` link selects the file in Explorer and is never opened; other links open with the system handler. A `file://` link counts only with an empty or `localhost` host. Upstream also takes the machine's own host name, and it ignores the macOS auto-mount roots `/net`, `/Network` and `/home`, which are ordinary folders on Windows.
  - A link URL must be printable ASCII as written. A raw space or non-ASCII character makes the link a plain label; percent-encode it.
  - Markdown is parsed with Markdig (CommonMark, pipe tables and strikethrough), not Foundation `AttributedString(markdown:)`. A raw HTML block inside a quote or a list item keeps the quote bar and the item indent; upstream draws it with neither, because Foundation gives an HTML block no block context.
  - Markdig refuses block nesting deeper than 128 containers (about 127 nested quotes or 63 list levels) and inline nesting past about 12000 unmatched brackets. Past those limits upstream lays the message out; the port shows it as plain rows.
  - A `file://` link with a colon after the drive (an NTFS stream such as `C:/x:stream`) or a drive-relative path (`C:x`) is drawn as a link and does nothing on Ctrl+click.
- `keymap.list` and `keymap.run` (`result.keymap`, `args.name`): the resolved keymap a script reads through `agtermctl keymap list`, and a custom command it starts through `agtermctl keymap run NAME` (upstream `f4b7a4aa` and `49628f8a`).
  - `chord` is the Windows spelling of the `keymap.conf` syntax: `ctrl`, `alt`, `shift`, then the key, with `cmd` and `ctrl` both shown as `ctrl`. `new_window` shows `ctrl+alt+n` where upstream shows `cmd+opt+n`, and an unmoved action shows its Windows default. `overridden` compares the Windows keys, so `map ctrl+alt+n new_window` is not an override. A command's `shortcut` is shown as written in the file, as upstream does.
  - `diagnostics[]` holds the parser diagnostics and then the Windows shadowing diagnostics that the Keyboard Shortcuts view shows. Upstream has only the parser's. `keymap.reload` still counts the parser's.
  - Left out: `menu[]` (the port has no macOS menu with key equivalents), chord alternatives and `--repeat` (the port has neither, so `alternates` is never written and a command's `repeats` is always `false`), and running from the session of an HTML page (no HTML overlays).
  - The list is the keymap last loaded from `keymap.conf`, the one every window arms, not a second parse of the file. A window applies a reload a moment later, so `keymap list` and `keymap run` already see the new file when `keymap reload` returns.
  - `keymap.run` runs in the window that owns the target session, as the custom command palette would, in the focused primary or split pane. The target session need not be the active one and is not selected. The reply comes after the process started or failed to start. A start failure answers `NAME did not start: REASON` and also queues the `Command failed` InfoBar.
  - The headless host answers `keymap.list` from its own last load and `keymap.run` of a known name with `custom commands are not available` (an unknown name gets `no custom command named X` first).
  - `commands[]` also carries `errorHud`, `errorPosition` and `errorPane`, see the next entry.
- `--error-hud`, `--error-position` and `--error-pane` on a `command` line of `keymap.conf` (upstream `9247b96f`, `17e37f38`): a failure panel for a custom command.
  - `keymap list` reads the options back: `errorHud` and `errorPosition` are always written, `errorPane` only when set. The human row adds `--error-hud --error-position POS` and ` --error-pane PANE` for a command with `--error-hud`.
  - Only a command with `--error-hud` captures stderr. It goes to a temp file, not a pipe, so a background process that the command started cannot hold the report back. The file is made with `CreateProcessW` and an explicit list of inherited handles. The last 16 KiB are read after the exit and the file is deleted. The stderr line is read as UTF-8, or as the console OEM code page when it is not valid UTF-8; upstream reads UTF-8 only. When the temp file cannot be created, the command runs without capture and the panel shows no stderr line, as upstream does.
  - On a non-zero exit, or when the command does not start, the panel is a HUD over the session for 10 seconds. Its text is `NAME: exit CODE` or `NAME: START ERROR`, then the last usable stderr line. A command that does not start also shows the `Command failed` bar, as before.
  - `keymap.run` of a command with `--error-hud` shows the panel too. The reply still says only that the process started.
  - Any overlay or HUD already open on the session keeps its slot, and no panel opens over it (the HUD open is refused with `overlay already open`).
  - A command without `--error-hud` that exits non-zero shows nothing. Upstream posts a macOS notification banner for it.
  - `--repeat` is not adopted, so it is not among the options.

Commands and fields that upstream does not have. `parity/windows-only.json` lists them for the parity tests, and a test checks that none of them exists in `docs/upstream/surface-v0.36.0.json`. None of them changes an upstream command, field or error string.

The title bar and the sidebar background follow the global theme; the sidebar rows of a workspace with its own theme show that theme's colors (see the sidebar theme colors below).

## Help menu: installing the command line tool, agent skill and status hooks

Upstream's Help menu has *Install Command Line Tool…*, *Install Agent Skill…*, *Install Agent Status Hooks…*, and *Developer Documentation…*. This port has no menu bar, so the title bar has a Help button, the last one on the right and always shown. It offers the three installers in that order; Developer Documentation is not ported. The command palette offers the same three installers as app commands, not builtin actions. Agent status hooks install a `cmd.exe` adapter under `%USERPROFILE%\.config\agterm\agent-status\` for Claude Code, Copilot CLI and Pi; the Copilot CLI hooks are installed only when `~\.copilot` exists, and the Pi extension only when Pi is configured. The Claude `PermissionRequest` hook sets `blocked` when a prompt opens, alongside `Notification[permission_prompt]` for other prompts; this adopts upstream change umputun/agterm#721 after the `7df70fe` pin. An existing Claude Code settings file is backed up, then rewritten with JSON indentation when its hooks change. Pi's status hook allows five seconds for a cold Windows CLI start, instead of upstream's one second. The installer refuses paths with cmd.exe-unsafe characters (`%`, `!`, `^`, `&` or `"`) rather than install a broken hook. Codex status hooks and process-level shell status are not installed: the upstream Codex permission watcher uses POSIX tools and a visible-terminal probe, while PowerShell's existing prompt integration only sees command completion. The Pi extension is not checked against a real Pi installation on this machine. The installer changes no control-API command, wire field, CLI flag, or `AGTERM_*` variable.

- The command palette (Run an Action…) lists the same three installer items. They are app commands with the ids `app:install-command-line-tool`, `app:install-agent-skill`, and `app:install-agent-status-hooks`, not builtin actions: a keymap cannot bind them and no control command runs them. The 41 builtin actions and `parity/surface.json` do not change.
- Each item runs the install and shows the result in a dialog with an OK button, as upstream shows an alert.
- *Install Agent Skill…* copies the skill files that the build embeds from `plugins/agterm/skills/agterm` to `~\.claude\skills\agterm` and `~\.codex\skills\agterm`, and to `~\.copilot\skills\agterm` when `~\.copilot` exists. The rules for Claude Code and Codex are upstream's; Copilot CLI is added after them and does not change the fallback: with none of the three directories present, the skill goes to Claude Code's. The dialog text is upstream's plus one paragraph: use this install or the agterm plugin, not both. See "Agent skill" below.
- *Install Agent Status Hooks…* writes Copilot CLI hooks to its own file `~\.copilot\hooks\agterm-win-status.json`, which Copilot CLI loads as user hooks. Copilot CLI does not read the Claude Code hooks in `~\.claude\settings.json`. The events, measured with the real `copilot` 1.0.105:
  - `userPromptSubmitted`, `postToolUse` and `postToolUseFailure` set `active --blink`; `agentStop` sets `completed --auto-reset`.
  - `notification` with the matcher `permission_prompt` (a tool permission prompt) or `elicitation_dialog` (the agent asks the user a question) sets `blocked`.
  - `permissionRequest` is not used: Copilot CLI fires it also for tool calls it allows without a prompt.
  - The file belongs to agterm-win: a rerun with no change leaves it as it is, a changed file is backed up to `.bak` and rewritten, and a file that is not valid JSON or has a hook that is not agterm-win's is left untouched with a warning. Without `~\.copilot` the dialog says Copilot CLI is not installed, without a warning.
  - The path is always `%USERPROFILE%\.copilot`; `COPILOT_HOME` is not read.
- *Install Command Line Tool…* puts `agtermctl` on the user `Path` instead of linking it into `/usr/local/bin`. It needs no administrator rights.
  - The app adds the folder of `agtermctl.exe`, which ships next to `agterm-win.exe`, to the `Path` value in `HKCU\Environment`. The compare ignores case and a trailing `\`, and it expands `%VARIABLES%` in each entry, so a folder that is already there, also as `%LOCALAPPDATA%\…`, is not added again.
  - The value keeps its registry type: `REG_EXPAND_SZ` stays `REG_EXPAND_SZ` and `REG_SZ` stays `REG_SZ`. It is read without expansion, so `%VARIABLES%` in it are written back as they were. A missing value is created as `REG_EXPAND_SZ`.
  - After the write the app broadcasts `WM_SETTINGCHANGE` with `Environment`. Explorer reloads the environment, so programs started from it after that see the new `Path`.
  - The app also adds the folder to its own process `PATH`, so panes it opens after the install find `agtermctl`. Shells that were already open, open agterm-win panes included, keep their old `PATH`; the dialog says to open a new terminal.
  - The dialog text is not upstream's, because upstream's text is about `/usr/local/bin`.
  - A build without `agtermctl.exe` next to the app, such as a debug build under `artifacts\bin`, answers `agtermctl is not bundled in this build.`

## Ported live-test coverage

`LiveSplitE2ETests.Promoted_main_pane_does_not_clear_fresh_split_right_status` ports the upstream promotion regression through real ConPTY shells and the WebView2 user-keystroke bridge. It waits for the status-clear callback to finish before asserting that the new right pane stays blocked, then checks that a key in that right pane clears its status. It does not test WinUI keyboard focus. Entering session zoom or changing its target closes the window's active session search. A background session target also has its own search closed. Leaving zoom does not reopen either search. Quick-panel zoom is independent and leaves session searches unchanged.

### Detached quick panel and global hotkey

Adopts upstream `f8679fde` (umputun/agterm#441) and the quick-zoom test correction `52f74f4d`. Existing commands, arguments, tree fields and error strings are unchanged; their app-level semantics replace the former per-window layer. This adds no entries to the pinned or adopted wire surfaces.

One application-owned, topmost WinUI tool window holds a separate WebView2 page and retained ConPTY shell. It is absent from the saved window index, taskbar and Alt+Tab. The HWND receives global-hotkey messages before the lazy page or shell exists. Human summons dismiss on blur; control `quick show` and toggle-on pin the panel, including an already-visible human summon. Hide clears panel zoom and pinning, not the shell. Shell exit discards it. Closing the first ordinary window does not destroy quick; closing the last closes the tool window and ends the app.

The quick page uses the global theme, not a workspace theme. Hide/show and theme changes preserve its font zoom. An explicit config reload resets it to the configured base font, as it does for ordinary panes. Its close, zoom and font chords act on quick; other application chords and session-switcher keys use the current ordinary window's command router. Creating or switching an ordinary session does not transfer keyboard focus. Shortcut help activates that ordinary window to show its XAML overlay. Custom-command chords use the current ordinary window's session context and the quick pane's selection.

`surface.zoom --target quick` expands the visible panel to the monitor work area. It ignores `--window`; a hidden panel answers `surface not available: quick` for every mode. Bare/active wire zoom always resolves a session surface. Panel and session zoom can coexist; app-level `quick` takes precedence in `zoomedSurface` while panel zoom is active. Session searches and ordinary-page rendering continue beneath quick. A newly pending GUI picker or question in any window hides even a pinned panel; the central show gate prevents summoning over the active window's GUI modal.

Windows needs an activating window for WebView2 keyboard input; it cannot reproduce macOS's non-activating NSPanel. On hidden-to-shown, the panel records the foreground HWND. An explicit hide restores that valid HWND only if quick still has foreground focus. Blur never raises a window over the application the user clicked. `SetForegroundWindow` is best effort under Windows foreground-lock rules. Denied activation of a pinned control-show panel is expected: it is traced without a failure notice, and the panel does not own the keyboard. A denied human summon still reports a failure notice. Denied focus return is trace-only because the app cannot override the foreground lock. No keyboard hooks, synthetic input or input-queue attachment are used.

The optional keymap line `global-hotkey ctrl+opt+space` uses `RegisterHotKey` with no repeat. It accepts one modified chord, not alternatives or leaders. The last valid line wins. One app registration is replaced or removed on keymap reload and unregistered at shutdown. OS registration errors include the chord and Win32 error in app diagnostics; they do not change the pinned keymap parser count or wire schema. The same shortcut in a second isolated app instance can fail without disturbing the first registration.

The existing supported virtual-key map matches ANSI positions on US and Russian layouts. On remapped Latin layouts such as Dvorak, a global hotkey follows the virtual key, not the physical position. Local shortcut decoding is unchanged. No low-level keyboard hook or foreground-layout re-registration is used.

Show uses the monitor under the pointer. The normal frame is centered in its work area, capped at 90% of that area and 1100 by 700 DIP. Quick zoom uses the whole work area, not the taskbar or WinUI fullscreen presenter. Placement converts DIP once using the target monitor DPI and accepts negative monitor origins. Showing, changing panel zoom, DPI changes and display/work-area changes recompute placement.

Later upstream changes were reviewed separately. `b4ec8ef5` corrects skill `quickVisible` readback; the port already uses `.result.tree.quickVisible` and retains it. Configurable `quickTerminalSizePercent` (`2683dbdc`, umputun/agterm#459), Metal hide/show memory changes (`b8f20f03`, umputun/agterm#492), F1-F20 keymap grammar (`47886daf`), remote quick cwd (`2e482023`) and cursor-column control (`2279c722`) are not included.

`LiveWindowControlE2ETests.Runtime_close_and_reopen_keeps_cursor_continuity` uses the application host and its shared event ring without OS windows. It checks the same event run across close and reopen, contiguous global sequence numbers across cursor reads, and the five upstream status/session event kinds in order. Coalesced `tree.changed` events also consume global sequence numbers, so the test checks continuity before filtering those structural events. Tests whose assertion requires WinUI row clicks or OS keyboard focus remain skipped; control-channel typing does not cover those assertions.

`LiveWindowControlE2ETests.Notification_badge_toggle_hides_and_shows_badge_without_losing_unseen_count` covers the extracted `SidebarBadge` render predicate with notification counts read through the application pipe. The WinUI row uses that predicate. Disabling `notificationBadgeEnabled` hides the badge without clearing its count, and notifications received while hidden still count.

`Refocusing_window_clears_shown_session_badge_without_a_session_switch` and `Refocusing_window_keeps_nonfocused_session_badge` cover the shared activation policy and host state path. WinUI reports the focused pane from each accepted layout. Activation clears unseen for the session whose main or split surface has accepted focus, even when another session is selected. `Activation_clears_background_focused_pane_owner_not_selected_session` checks both main and split panes in background-session zoom and dashboard layouts. The focused pane's session clears while the selected session keeps its count. Other nonfocused sessions, other windows, and sessions behind an overlay, scratch, or quick pane stay unchanged. This follows the main/split refocus callbacks in upstream `GhosttySurfaceView.clearUnseenOnRefocus` and `agtermApp` at pin `7df70fe` and upstream HEAD. The callback runs off the UI thread under the store gate, without selecting a session. Returning from another app also applies the policy when the cached frontmost window ID has not changed. `window.select` waits for it before replying.

These three ports use component-level policy checks and the application host. They do not automate OS activation events, Settings clicks, or rendered XAML. Separate guards cover covered-pane activation, the `window.select` readback, and a busy store gate. The six WinUI keyboard/click placeholders and six platform-only placeholders remain skipped.

The activation and PowerShell readline regressions also run in isolated child test processes with one thread-pool worker. The activation test uses dedicated holder and caller threads with direct signals while the store gate is held. The readline tests wait for shell exit and output drain on a dedicated thread under one 60-second deadline. A real timeout reports the captured terminal output and both task states. These test-only changes leave production scheduling and suite parallelism unchanged.

Each WebView2 test fixture uses its own temporary user-data folder and browser process group, so the nonparallel environment collection does not wait on the previous collection's browser shutdown. Asynchronous Load errors and an early UI-loop exit fault startup; the unchanged 60-second startup deadline reports the initialization stage, profile, and STA thread state. Shutdown failures are logged, not thrown. A fixture deletes only its own profile, after verifying that its browser process has exited; otherwise it retains the folder and reports why.

## Agent skill

The skill in `plugins/agterm/skills/agterm` is this repository's copy of upstream's skill, adapted to Windows.

- The examples stay in bash, as upstream, so the diff against upstream stays small. Claude Code on Windows runs its Bash tool through Git Bash. Codex on Windows runs commands through PowerShell, so `SKILL.md` has a PowerShell section: `$env:AGTERM_SESSION_ID` instead of `$AGTERM_SESSION_ID`, quoting of JSON arguments, and the `AGTERM_ENABLED` check.
- Upstream sections that the skill does not have:
  - Inline images and `scripts/show-image.sh`. They need kitty graphics, and agterm-win does not support kitty graphics.
  - `log show`. It reads the macOS unified log. agterm-win writes no log file, so the skill says to read its `Trace` output with a debug-output viewer such as DebugView.
  - Homebrew. There is no Homebrew cask for agterm-win.
  - Attaching a session from another Mac. It needs zmx live sessions, and agterm-win has no zmx (`docs/upstream/delta-7df70fe-to-v0.36.0.md`, section 1).
- The plugin channel. As upstream, the repository is also a plugin marketplace. `.claude-plugin/marketplace.json` serves Claude Code and Copilot CLI, and `.agents/plugins/marketplace.json` serves Codex. Both list the plugin `agterm` from `./plugins/agterm`. It holds the same skill files that *Install Agent Skill…* copies.
  - The plugin `version` is the plugin's own, not upstream's and not the app `<Version>` in `Directory.Build.props`. A person raises it by hand when the skill changes, in the three manifests, and `SkillTextTests` checks that they are equal. Claude Code does not update an installed plugin while the version string stays the same, so an app release that leaves the skill alone does not update the plugin.
  - A user installs the skill one way: from the app or as a plugin. With both, the agent loads two copies of the skill. The *Install Agent Skill…* dialog says this too.
  - Copilot CLI reads personal skills only from `~/.copilot/skills` and `~/.agents/skills`. *Install Agent Skill…* installs to `~/.copilot/skills/agterm` when `~/.copilot` exists; a Copilot CLI user can also install the plugin.
- `allowed-tools` is `Bash(agtermctl:*)`, not upstream's `Bash(agtermctl *)`. Claude Code reads both forms the same way. Copilot CLI turns `Bash(agtermctl *)` into a rule for the literal command prefix `agtermctl *`, which matches no real call, so it asked before every `agtermctl` command. With `Bash(agtermctl:*)` it runs them without asking, in an interactive session; measured with `copilot` 1.0.105. In `copilot -p` a skill's `allowed-tools` is not applied; there `--allow-tool "shell(agtermctl:*)"` does it.
